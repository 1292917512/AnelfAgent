# Minecraft 陪玩功能评审与实施计划

记录日期：2026-10-08；最近更新：2026-10-09。当前阶段：M1/M2、M3 制作、指定箱子补给、表面采集返程及显式区域缺料采集再制作均已提交部署并完成专项验收。M0 已完成请求观测与首批 125 条真实模型链路记录，严格冷/热缓存控制仍未完成。M4 首批工具作用域、背包/停止回执和单任务事件交接已实现，最终版本完成 16 次隔离真服验收；M3 熔炉、M5/M6 待完成。部署事实、覆盖范围和剩余边界见文末执行记录。

目标是让机器人可靠地完成「做一把木镐，跟我去挖矿」这样的完整任务：能自行准备材料和工具，执行时能聊天、及时停止、处理危险，按实际获得的物品报告结果，并且能够返回和补给。

主要短板是完整任务能力不足、游戏行为控制权分散，以及模型参与过多操作细节。保留 AnelfAgent 的对话和记忆能力，复用 Mineflayer 生态，在现有执行器中逐步补齐任务与生存行为。

## 当前实现与不可回退的保护

| 范围 | 当前已有能力 | 仍然存在的边界 |
| --- | --- | --- |
| 陪玩交互 | 游戏聊天和私聊、局域网发现、跟随、快捷停止、交付物品、观察背包与环境 | 普通多步任务仍常依赖模型或 `mc-worker` 逐步调用工具 |
| 合成 | 木制工具/工作台/木棍后台制作；可显式授权区域补采最少原木、返程后按真实库存制作；配方/设施预检和临时格子收尾 | 默认只用背包，配方受锁定依赖限制；不自动启动箱子补给，断网或强杀进程无法保证收尾 |
| 箱子补给 | 指定可见普通箱子/双箱/木桶的卸货和补齐工具、食物、火把；整批预检、最低保留量、双方库存核验与取消收尾 | 不自行选箱/走路/返程，不是跨玩家原子事务；容器破坏、断网或来源被占满时无法保证收尾 |
| 放置 | 检查支撑点、朝向、整方块与自身碰撞 | 复杂施工、位置选择和失败重规划仍不完善 |
| 挖掘与采集 | 等服务器确认移除；工具与可见面检查；区分挖掉数量和背包增量 | 掉落物未捡到时必须如实报告，不能把挖掘完成等同于收集完成 |
| 表面采集与返程 | 在明确区域采集原木/圆石，按新入包计数，返程后可存入指定箱子，出发前可先补物资；原木缺料采集可由制作任务组合 | 仅同高平坦通路及脚部至上两格目标；不自动辨别人造建筑，不是完整伐木或矿脉搜索器 |
| 可往返矿洞 | Node 后台执行台阶和直矿道，记录路线、检查回程、保存检查点、播报终态 | 当前主要是矿道施工，尚无按矿种寻找矿脉、分支开采和自动补给闭环 |
| 生存反应 | Node 本地危险观察与有限避险；制作中受伤会先收尾再自救，旧请求不能续跑 | 未知地形、无岸水域和无出口包围无法保证脱困；只覆盖代表性的合成抢占组合 |
| 位置记忆 | 家、普通标记、最近矿洞检查点 | 家和普通标记仅在内存；矿洞检查点不是完整的世界设施目录 |

后续所有阶段都必须保留以下约束：

- 挖掘完成必须有服务器方块更新事实；资源到账必须有背包或明确交付事实。返回任务 ID 只表示已启动。
- 合成失败和正常断开尝试归还临时物品；背包放不下时报告失败，不自动丢弃材料。
- 普通寻路目前禁止挖路、搭柱和多格跳落；矿道地板与脚下支撑受保护。若将来增加特殊移动模式，必须明确适用范围并独立验证，不能全局重新开放危险动作。
- 矿洞当前宽 1、高 3，单次下降不超过 16 级，额外水平段不超过 32 格，有总执行预算。
- 挖矿最低脚部 Y 不低于服务器维度底界加 10；用户只能设置更高的下限。到下限后停止下降，只执行请求范围内的水平段。世界高度未知时拒绝施工，基岩按不可挖障碍处理。
- 高度下限只是施工边界，不代表该高度没有岩浆，也不代表适合所有矿种。
- 返程路径需要真实可步行；返程受阻时报告实际位置和原因，不能声称已经回到入口。
- 死亡、断线、切换维度后不自动恢复危险施工；恢复前重新验证世界、资源和路线。

当前有离线动作与频道测试，部分测试使用真实依赖和模拟协议或移动状态。它们不能替代真实服务器上的地形、延迟、怪物、断线和返程验证。本文新增的阶段均不因既有测试通过而自动视为完成。

## 问题证据与判断范围

### 模型编排等待

历史样本来自本地 `logs/anelf.log`，日期为 2026-10-08。日志可能轮转，检索时使用时间和事件名称，行号只作当时定位。

| 时间 | 事件 |
| --- | --- |
| 20:47:06.677 | 收到玩家「你去挖几个石头吧」 |
| 20:47:06.685 | 注入 177 个工具，其中 always 90 个、Minecraft 87 个 |
| 20:47:08.710 | 检索规划达到 2 秒超时，回退原查询 |
| 20:47:16.667 | 一次模型调用的输入为 46688 token，缓存读取 28544 token |
| 20:47:25.198 至 20:47:25.200 | 执行 `get_state`，约 2 毫秒 |
| 20:47:25.761 至 20:47:25.775 | 执行 `find_blocks`，约 14 毫秒 |
| 20:47:51.465 | 达到 8 轮安全上限，强制结束 |

从收到消息到首次游戏状态查询约 18.5 秒。该样本支持「多轮模型编排和前置处理造成明显等待」，不能把这段等待归因于状态查询或 MCP 传输本身。后续模型调用有较高缓存命中，不能据此断言缓存失效。

此样本发生在新挖矿脚本上线前，不是新脚本的性能测试，也不能当作所有请求的平均延迟。该次请求已走直接回复路径，不应再假定每条游戏消息都经过额外元决策调用。

### 轮询和事件处理

- `channels/minecraft/reflexes.py::run` 依次查询连接、角色和寻路状态，处理动作后再休眠；实际观察间隔包含本轮工作时间。部分动作的等待会延迟下一次观察。
- `channels/minecraft/adapter.py::_poll_once` 又查询连接并读取事件，然后逐条等待分发。部分快捷命令直接等待工具完成，后续停止或聊天事件可能排在其后。
- 当前逃跑主要由血量下降触发；溺水、火焰、逼近的危险等应有专门判断。未知血量也不应直接等同于已死亡。
- 自动进食已有执行器插件；迁移反射层时先核对已有行为，避免双重控制。

### 动作控制冲突

现有动作锁与挖矿专用 BUSY 保护提供了局部互斥，但跟随、制作、采集、逃跑、空闲行为尚无统一的优先级及暂停恢复契约。

已确认的语义冲突：`adapter.py::_cmd_stay` 声称只停移动、不取消采集，但调用 `stop_pathfinding`；当前挖矿包装将该工具视为取消任务。需要把「待着」「停止」「暂停」「返程」的语义和实际控制权统一。

### 矿道执行中的重复工作

`runtime/mining-task.cjs` 在推进时检查返程，行走前再次检查并寻路；返程逐个路点执行时还会重复检查整段矿道。每次推进另有固定 600 毫秒等待，32 次推进仅这项等待就累计 19.2 秒。这是代码中的固定时间计算，不是实际总耗时测量。

可以考虑按方块变化使路径缓存失效、增量检查、复用移动规则和事件驱动拾取。优化前先测各部分占比，保留服务器确认和返程检查的语义。

### 游戏卡顿与维护成本

安装脚本把寻路总预算从 5 秒延长到 30 秒。单次计算切片不变，只能说明每次让出事件循环的预算不变，不能推出总 CPU 开销不变。需要分别测量 Node 事件循环延迟、寻路计算、区块处理，以及游戏帧率或服务器 tick，不能将聊天等待和游戏掉帧混为一谈。

当前兼容补丁会修改锁定依赖的构建产物。版本锁定、锚点检查和回归测试需要保留；后续把新增业务能力收敛到自有执行器模块，将必要协议补丁集中管理，降低升级时的漂移风险。

## 目标架构与职责

玩家意图由 AnelfAgent 对话层理解，再通过 MCP 启动高层任务；Node 执行器负责任务步骤、生存反应和游戏状态验证，将进度与终态事实回传频道。任务执行期间，对话层仍能聊天和接收新指令。

| 层 | 应负责的工作 |
| --- | --- |
| 对话与记忆 | 理解任务、处理歧义、保留人设和偏好、解释异常、决定新目标 |
| MCP 接口 | 启动、查询、停止和恢复高层任务；提供受控的观察与诊断能力 |
| Node 任务控制器 | 分配移动、装备、交互等控制权；仲裁行为、记录进度、取消和收尾 |
| 本地生存行为 | 读取本地游戏事件和状态，及时应对危险，必要时抢占任务 |
| Mineflayer 生态 | 协议、物理、寻路、工具选择、合成、采集等成熟底层能力 |
| 持久化状态 | 保存世界和维度、位置、设施、任务检查点；恢复时重新校验 |

任务契约需要包含：任务 ID、发起人和世界、阶段、目标与实际数量、当前控制权、停止或失败原因、是否返回、是否满足恢复条件。阶段至少区分执行、暂停、返程、完成、失败、取消、中断；具体类型和兼容映射在 M1 确定，不能同时维护两套事实。

仲裁顺序拟为：玩家明确停止优先终止当前工作，其次为紧急生存、当前任务、空闲活动。「停止工作」不会自动恢复被取消的任务；是否保留必要自救行为必须在接口和回复中明确，避免自动行为马上重新开工。正常暂停只有在安全检查通过后才允许续跑；死亡、断线与换世界继续要求明确恢复。

Python 继续遵循项目依赖方向和统一生命周期；MCP 保持现有入口。无需为了本次优化更换通信协议或重写整个智能体内核。分钟级提醒可用于长期目标跟进，游戏动作推进和紧急响应由本地任务及事件负责。

## 场景验收与验证入口

贯穿各阶段的主场景为「做一把木镐，跟我去挖矿」。在同一固定世界副本中覆盖以下变化：

| 场景 | 必须观察的结果 |
| --- | --- |
| 身上只有原木，附近没有工作台 | 准备配方材料和工作台，制作结果到账，临时格子收尾 |
| 已有工作台或部分材料 | 复用已有资源，避免重复制作和错误材料计数 |
| 制作或采集中停止 | 及时停工、明确终态，临时材料不主动掉落，旧任务不会自行重启 |
| 聊天或模型响应缓慢 | 本地停止和生存行为继续工作；可以查询真实任务进度 |
| 怪物逼近、入水、着火、卡住 | 按优先级应对，危险处理不与普通动作争抢控制权 |
| 地下遇水、岩浆、落沙、基岩和最低 Y | 不破坏脚下支撑、不继续危险下降，停止或安全返回并说明原因 |
| 背包满、工具不足、火把不足 | 按已配置设施补给或准确报受阻，不能虚报资源到账 |
| 返程路被玩家堵住 | 不能报告已经返回；保留位置和受阻原因 |
| 断线、应用正常关闭、重启、死亡、换维度 | 区分可收尾与不可收尾情况，保存事实，不盲目自动恢复施工 |
| 局域网换端口或同端口换世界 | 不丢失可确认的世界记录，也不串用另一世界的矿道 |
