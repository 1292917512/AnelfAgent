# 上下文缓存与用量排查

本文只在修改上下文组装、前缀缓存、用量统计或压缩逻辑时阅读。它描述排查顺序与红线，不记录某次
供应商事故。LLM 层机制详见[模型分册](llm-and-models.md)。

## 先区分三层问题

LLM 前缀缓存命中率是本项目的核心成本/性能指标。缓存工程分三层责任，排查时**先定位层再下结论**，
不要默认「缓存崩了」：

1. **客户端字节稳定性**（完全可控）：变动率排序组装 + tools 冻结 + 摘要窗口 + 单一装饰点。验证 =
   快照 section 哈希 diff + **PrefixGuard 运行时哈希链**（records.jsonl 的 `prefix_drift` 字段定位
   首个断裂消息）
2. **供应商缓存行为**（不可控）：磁盘缓存传播延迟/驱逐/节点亲和。判读特征 = prefix_stable=True 而
   read 浮动、1~2 轮自愈（「平台波动」）。**合法断裂单独标识**：折叠/压缩是已知的前缀整体重写，
   完成点经 `prefix_guard.note_legal_break(scope, reason)` 登记（fold/compress）——清空该 scope
   全部基线，并在 120s 窗口内让快照记录携带 `legal_break`，与「平台波动」区分
3. **统计与展示口径**：kind 分桶 / age_sec 回声 / unobservable / 单次钳制率平均；缓存命中率使用
   归一化的 `cache_read / total_input_tokens`，不把不同供应商是否把缓存读写计入 prompt 的口径混算

## 上下文层红线清单

改动记忆/召回/画像注入时逐条自查（前四条有不变量测试锁定：
`tests/unit/agent/mind/test_cache_layer_invariants.py`）：

1. **vol ≤ 30 禁入**：记忆召回/画像/关系/技能/状态/短期记忆内容块的 volatility 必须 > VOL_HISTORY(30)
   （stable/summary/conversation 是缓存前缀，一个字节变化即断裂）。新增 `@context_block` 时先想
   「这块多久变一次」
2. **pin 块独立成消息**：永久记忆块与召回/检索块必须分消息返回（`_format_unified_results`），
   recollection 的 startswith 提升只捕获纯永久块；合并成一条会把每轮变化的召回内容带进 context 层
3. **时间戳只准日期粒度**：召回渲染用 `%m-%d`/`%Y-%m-%d`（`_format_memory_time`）；秒级/计数器类
   易变字段不得进入任何注入块（状态计数器隔离在 status 层是刻意设计）
4. **fail-open 不注入错误文案**：召回/画像/关系/技能匹配任一异常 → 该块为空（管线跳过空内容），
   禁止把异常文本写进上下文——错误文案每轮不同，等效于注入易变内容
5. **session_token 暗坑**：`security_session_token_enabled` 开启后历史消息逐条包裹每轮随机的令牌，
   conversation 层字节全变、历史锚点恒失效——排查命中率时先确认该开关状态
6. **legacy 布局暗坑**：`context_tail_injection_enabled=false` 时动态块移到历史之前，召回结果直接
   击穿历史前缀——缓存友好布局依赖 tail injection 保持开启
7. **PreCompact flush 只写 DB**：压缩前的记忆抢跑提取（`_precompact_flush`）只写记忆库，不触碰任何
   prompt 分层内容；压缩本身的 invalidate+prewarm 走既有机制，记忆侧改动不得在这条路径上新增
   prompt 层写入

## 近期执行诊断

`get_conversation_diagnostics` 提供当前会话及明确指定 scope 的消息摘录、运行中步骤、模型首响应/
用量、工具结果与投递回执。Web「上下文 → 执行诊断」及受现有 API 认证保护的
`GET /api/context/recent?scope=...&limit=3&steps=12&messages=8` 共用同一查询面。
`turn_id` 可定位具体轮次；空 scope 的 HTTP 查询返回近期各会话，AI 工具默认当前会话，显式
`scope="*"` 才查询全部。消息按提交 ID 排序，不把相同用户的不同频道或子会话合并。
工具在执行中查询时优先返回自身轮次，并返回 `current_turn_id`，避免并发子代理挤掉当前执行。
AI 查询默认两轮、每轮八步和六条消息；诊断工具自身只记录耗时与状态，不递归摘录自己的返回。

执行诊断由既有事件生成，独立于 Web 和详细追踪开关，最多保留 40 轮、每轮 80 个步骤、每段
500 字符摘录，重启清空。它不保存完整提示词、推理或流式增量，不产生模型请求。消息复用
`SqliteBackend` 已加载的内存窗口；未加载或已淘汰明确返回 `loaded=false`，查询不补读数据库、
不更新已读水位。消息窗口本身按原会话规则运行，不改变持久化和跨频道实时感知。

`duration_ms` 为本轮实际经过时间，异步步骤可能重叠，不可求和；`active_steps` 包含仍在执行的
步骤，包括父轮结束后继续运行的异步钩子。`omitted_steps` 表明查询裁剪或淘汰，不能把未显示当作
未执行。模型生成文本不证明送达，投递以 `delivery` 回执为准；缺失回执表示未观测，不能判断发送
失败。缓存字段缺失或 `cache_observable=false` 表示不可观测，不能当成 0%。诊断覆盖思维调用入口，
不代表所有组件的供应商请求总量。旧轮次完整操作清单仍由 `get_execution_log` 按需读取。
`active_run_ids` 列出所选范围中仍有工作进行的轮次，超出默认返回数量时可用 `turn_id` 查询；
淘汰优先移除没有运行中步骤的历史，所有记录仍受总上限约束。

## 异步召回与轮内快照

收发消息经现有存储入口提交后同步更新内存窗口；每次模型调用前，以本轮实际历史快照的
`_source` 水位读取内存中的全部新增收发消息，再追加到当前工具链。取数位于压缩与动态媒体准备
之后，不以 20 条或字符预算把已收到的补充、纠正留给后续模型轮次。水位随快照传递，不能使用其他
读者可推进的全局已读状态。普通轮次不查询数据库；回复起点的摘要/别名/折叠历史仍按原有规则
构建，冷窗口、淘汰或积压超窗才补读持久化记录。
窗口属于 `SqliteBackend` 的统一写入面，不另设消息总线或频道副本；最多 128 个 scope，每个
保留 256 条、256,000 字符，落后读者按水位补读而不丢消息。编辑/删除/清空、数据库管理页写入、
迁移与连接关闭均失效相关窗口；已经发出的模型请求使用独立快照。
换向折叠标记的水位覆盖整个弃置段，不能停在段首，否则轮内刷新会把已折叠内容当作新消息重放。
本轮正常结束前再次检查插话，避免最后一次模型请求期间到达的消息被留到下一周期。
待回复队列只消费本轮已覆盖的消息，跨会话感知不代表对方已被回复。
显式发送获得成功回执后，跨会话待办按本次模型输入的用户消息水位收束；网络发送开始前冻结水位，
期间到达的新消息继续待处理。失败、未知回执或模型未看到的目标会话不收束，当前会话的发送计数仍单独隔离。
实体通知若已随实时历史并入，不再从推送入口重复注入；兜底推送只清理已覆盖水位内的待办。

其他会话待回复的新私聊与群聊 @ 由 `cross_channel.py` 每轮从同一内存窗口读取，放在已有 provider 动态区；
按 scope/channel/role 标记身份与目标，包含同频道不同子会话。普通群聊、平台通知、已处理历史不进入该窗口。
候选来自待回复队列，沿用配置的会话数边界；所选会话读取完整未读段，不复用普通历史条数上限。
部分发送成功只推进已覆盖水位，期间到达的新消息仍可感知。
单个会话读取失败只跳过该会话，保留其他会话的实时感知。这些读取不重新执行记忆召回，不改写
stable/summary/history 与已执行工具链。

原生视觉的图片来源统一为本地路径、URL 或 Data URL，加载后的图片仍保留消息归属：入站图片附在
新用户消息，工具图片追加到完整工具回执批次之后，provider 画面位于原有动态区。工具内联数据在
文本预算处理前分离，不复制为大段普通文本。去重只检查当前上下文中的图片内容，不删除或重写历史，
也不因旧图已压缩掉而阻止重新加载。媒体处理规则保持静态，不按模型视觉能力改变稳定前缀。

跨会话历史召回与首轮记忆召回并发，复用同一查询向量。候选按显式用户别名关联及近期话题选择，
不凭跨频道同号或昵称推断身份；关联用户的历史不受近期活动窗口限制。Jev 使用当前对话正文及候选
话题判断检索是否必要，无配置或不可用时保留语义检索。检索各候选并发执行、独立降级，排除当前上下文已有内容。
结果携带来源与日期并明确标记为历史证据，不形成新待办。判断与检索耗时共用钩子执行记录，实时新消息不等待 Jev。

初始深探受首轮召回剩余预算约束，返回前收束任务；其结果经 `memory_deep_probe` 进入 provider 层。
轮中只针对本会话新增用户对话异步补查本地记忆与技能，不监听工具输出、内部独白或跨频道通知。
查询只取近期对话，Jev 只看短候选与对话证据；一批候选共享一次判断，无普通模型回退。
新事实只追加到有界快照，未变时字节稳定；已准备与已进入模型输入分别记账。
实时消息、跨频道感知和其他动态 provider 继续逐轮刷新，手动 `recall` 不受限制。

深探快照共享字符预算；账本属于消费结果的会话，查询标签不改变消费归属，未呈现事实不入账。
策略变更取消在途检索，已呈现内容保留；新对话使旧查询失效，回复结束回收全部状态。
补充结果不能回写历史或工具链，不触发额外主模型调用。新对话本身的消息并入顺序保持原样。

思考循环以 `ContextProviderRegistry.collect(fresh=True)` 每次采集零 I/O 快照，不复用其他轮次的
ContextVar 或两秒聚合缓存。常规观测调用仍可合并请求。provider 内容变化不得改写其前面的
stable、summary、conversation 与工具链，也不得在 provider 消息上设置缓存断点。
工作区的准备钩子显示检索和判断进度；深探快照实际进入模型调用组装后，才发布单独的
上下文观测事件。观测事件不回写模型消息；没有变化的快照不重复发布，也不另起主模型轮次。

缓存健康门同时覆盖固定前缀与新增召回尾部两种真实请求。命中率受供应商缓存粒度、写入传播与
驱逐影响；应同时检查前缀字节不变量和实际 usage，不能单靠其中一种判断。

## 用量与版本变更

反思与钩子的工具目录在整个执行周期内使用同一继承规则：保留已见工具顺序，新发现工具追加在尾部，
注册定义更新、禁用或前置条件失效立即反映到目录。继承目录只保持可见性，不绕过工具执行权限。
评估收益同时比较完成正确率、总调用时延、输入量与未缓存 token；命中比例不能替代任务成本。

修改 litellm 或用量解析时，先确认 `pyproject.toml` 与 `uv.lock` 的实际版本，再运行针对性缓存
集成测试：

```powershell
LLM_CACHE_E2E=1 uv run pytest tests/integration/test_llm_cache_hit_e2e.py
```

可用 `LLM_CACHE_E2E_MODELS=a,b` 缩小模型集合。litellm 的流式 usage 处理是脆弱契约（历史版本曾对
未收录模型用 tiktoken 估算伪造 usage：prompt 虚高 ~1.8 倍、completion 清零、details 丢弃），因此：

- pyproject 精确锁定版本（`litellm==x.y.z`，禁止范围符）
- **litellm 升级同步规范（机械门禁）**：版本变动必须运行全模型缓存与用量健康门并全绿后才放行——
  对配置内全部启用 chat 模型经真实 LLMClient 管线发两次同前缀流式调用，断言：两次 usage 均回报 /
  completion>0（伪造指纹）/ 含缓存口径 read+creation ≤ prompt（尺度混血指纹）/ 可观测时第二次
  cached>0 且命中 ≥0.7（判别区间：伪造尺度混血 ≈0.55、平台粒度损失实测下限 ≈0.78；暖调用按
  2/4/8s 递增窗口吸收供应商写读传播滞后）
- litellm 升级前必须验证 `litellm.ModelResponse()` 可实例化；1.96 起 `AsyncHTTPHandler.client` 变为
  已关闭即惰性重建的属性（取引用再判 `is_closed`，重复访问会拿到新池）

上下文占用、压缩触发和预算提醒使用归一化输入量（含供应商缓存读写的统一口径）。主对话经过统一
调用入口时只记一次用量（`chat_with_fallback(record_usage=False)`），委托调用的成本归属父会话；
一次性反思 scope 不产生孤儿统计行。口径细节见[模型分册·用量与观测](llm-and-models.md)。

## 修改后检查

工作区模型详情沿用供应商报告的输入与缓存读取量，并展示首个有效输出前后的客户端耗时。
空保活、角色和用量包不计作首响应；思考、正文及工具输出均计入。首响应前包含网络、排队和
服务端处理，首响应后仍包含传输与本地消费，不能将两者直接解释为纯 prefill/decode 时间。
非流式或未观测到有效输出时不推算首响应。高缓存命中而耗时较长时，应继续检查输出量和工具等待，
不能仅凭总耗时改变缓存层次、降低思考档位或删减上下文。

1. 对比 stable、summary、conversation、context 和动态尾部的消息快照
2. 检查 `_layer`、`_source` 是否只存在于内部消息，发送前是否经过 `normalize_for_send`
3. 先运行缓存不变量单测，再按模型和供应商需要运行集成测试
4. 将折叠、压缩、供应商不可观测和真实缓存波动分别标记，不能用「重启后变冷」推断缓存已清空
